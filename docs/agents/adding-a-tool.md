# Adding a new tool

Read this when you add or change an MCP tool. Code examples and patterns: [DEVELOPER.md](../../DEVELOPER.md).

1. **Use case first.** Put the logic in `internal/app/{domain}/` (typed input, repo-owned result). `internal/app/**` must not import mcp-go or the Forgejo SDK (depguard in `.golangci.yml`); reach Forgejo through the port in `internal/forge/`, bridged by `internal/forge/<domain>adapter/`.
2. **MCP adapter.** In `internal/operation/{domain}/`: a `mcp.NewTool()` definition, an argument struct (`json:"name"`, `required:"true"`), an optional `Validate() error` method holding the checks that ran before the credential lookup, a Binder that looks up the credential and builds the use case, and a run function that calls the use case. Register the tool with `pipeline.Handle(bind, run, opts...)` (`internal/operation/pipeline`), never with a per-domain `run` helper. **Decode rule (the one answer for a new tool):** the pipeline decodes; a domain never calls `decode.Lax` or `decode.Args` itself (`scripts/ci/check-decode-boundary.sh` fails the build on it). The default is lax; pass `pipeline.Strict()` to refuse a missing or mistyped argument, `pipeline.Lax()` to decode forgivingly whatever the package default, and `pipeline.WithRaw()` with `pipeline.Raw(ctx)` only for a tool that must tell an absent argument from a present null. **Number rule:** declare a number `float64` in the argument struct and read it through `internal/numarg`; never `int(...)` or `int64(...)` it. Two typed exceptions, each where a golden pins error text that depends on how the number was given: `any` (the dependency tools) and `decode.Arg` (the `edit_milestone` and `get_milestone` `id`, whose "id must be an integer between 1 and 9223372036854775807" is pinned by goldens). A reviewer checks a new tool against these two rules, not against the exceptions. Pass one hint annotation as the second `mcp.NewTool` argument: `annotate.Read()` for get/list/search/check/download, `annotate.Write()` for create/update/other writes, `annotate.Destructive()` for delete/remove/cancel (`internal/operation/annotate`). Add the tool's name and class to `expectedHints` in `internal/operation/annotations_test.go`; that test fails for a tool with no class. Numbers are `float64` in the argument struct and are read through `internal/numarg` (see DEVELOPER.md, Numeric arguments), except where a tool's error text depends on how the number was given: those type it `any` and pass it to the same module. **Lean marker:** give an argument `lean.Keep("clause")` in its option list, next to its `mcp.Description`, when its name and type do not show how to fill it in: a format (comma-separated list, RFC3339 time), an allowed-value list (`state`, `sort`, `type`), or a rule (mutually exclusive, empty clears it). The clause is one short phrase, at most 120 bytes, and is what `--lean` serves in place of the description. Never mark `owner`, `repo`, `index`, `page`, `limit` or `verbose`. `internal/operation/lean_test.go` fails for a marked argument with no description, a clause that is empty or too long, or a never-marked name marked.
3. **Register** in the domain's `RegisterTool(s *server.MCPServer, f forge.Factory)`. Then add the tool's name to its toolset in `internal/toolset/toolset.go`; the registry test fails for a tool in no toolset.
4. **New domain:** import and call it in `internal/operation/operation.go`.
5. **Pin it with tests.** `mcptest.SchemaSnapshot` and `mcptest.Golden` per tool, `mcptest.ArgsMatchSchema` per argument struct (`go test ./internal/operation/{domain} -update` writes the files), and use-case tests in `internal/app/{domain}/`.
6. **Go through the port.** The tool's Binder calls `f.For(ctx)` per request, after the pipeline has validated the arguments, and hands the port to the bridge. Exception: a tool whose Forgejo call sends no credential (`get_forgejo_version`) binds the factory directly instead of calling `For(ctx)`, because `For` refuses a request that carries no token of its own. A new endpoint is a port method, its adapter in `internal/forge/sdk/`, its fake and a contract case. Nothing outside `internal/forge/sdk` builds an SDK client or an HTTP request to Forgejo.
   **Escape API paths** in the adapter's raw-HTTP methods (`a.rawJSON`, `a.rawDo`, `a.raw.doAPIRaw`, `a.raw.doMultipart`): build the path with `forge.APIPath("repos", owner, repo, …)`, which escapes every segment. A hand-rolled `fmt.Sprintf("/repos/%s/…")` lets an owner containing `/` or `?` retarget the request at another endpoint; `scripts/ci/check-api-path-escaping.sh` fails the build on it. Append query strings to the `APIPath` result.
7. **Bound the output.** If response size depends on data (not tool semantics), the tool MUST satisfy [output-bounding.md](../design/output-bounding.md): client-controlled bound, resumability and documented parameters. A list use case gets its bound from the list module (`internal/app/list`): `list.Run` for a paged list, `list.Window` for a port that reports its own `has_next`, `list.Cut` for a list Forgejo does not page. It does no page/limit parsing or ceiling check of its own. Read raw page/limit arguments with `decode.PagingArgs`. Put the checklist from that doc under the PR body's Evidence section (the `/pr` template has no separate slot).
8. **Reference row.** Every registered tool needs a row in the tool table in [docs/reference/tools.md](../reference/tools.md), and every `forgejo://` resource template a row in the table in [docs/reference/resources.md](../reference/resources.md). `scripts/ci/check-readme-tool-coverage.sh` fails the build on a tool or template with no row: it compares the `…ToolName` constants and registered URI templates under `internal/operation/` against those two tables. The toolset and preset tables in [docs/reference/toolsets.md](../reference/toolsets.md) also list tools by hand, so add the tool there when its toolset membership changes; the registry test (step 3) checks the membership itself.
